    03 · Trust boundaries in execution

    Trust is a chain of separate decisions

    An authenticated agent can still process hostile content. Safe execution comes from deciding identity, input trust, and authority separately.

    01 · IDENTITY

    Who is acting?

    Agent roles and GitHub App installations make actions attributable and allow permissions to be scoped by role.

    Verify the caller and the workflow that requested access.
    02 · CONTENT

    What did it read?

    Issues, comments, pull requests, and agent output remain untrusted input, even when they came from a known repository.

    Treat content as data to sanitize, not instructions to trust.
    03 · EXECUTION

    What can it do?

    Sandbox policy, credential scope, network rules, and repository gates constrain the blast radius of a run.

    Limit authority before the runtime starts acting.
    03 · Trust boundaries in execution

    Credential delivery depends on the service

    Fullsend uses different boundaries for different integrations. Some runs have no runtime credential; others receive a scoped token or a real credential file.

    Prefetch + post-process

    Inputs arrive before the run. A host-side step applies the result afterward.

    OpenShell provider

    The runtime carries an opaque placeholder. The gateway resolves the credential at the allowed endpoint.

    Host file

    File-based auth can enter the sandbox. Network policy becomes the hard security boundary.

    Host-side service

    A scoped API mediates operations the provider model cannot express.

    the boundary moves with the integration

    Agent runtime

    One runtime, several credential shapes.

    GH_TOKENminted GitHub App token, scoped by role and repository
    model accessprovider placeholder, WIF-backed access, or a host-delivered file
    repository workspacefilesystem and network policy limit what the run can reach
    The question is not “are there credentials?” It is “which credential reaches which boundary, for which operation?”

    03 · Trust boundaries in execution

    Minted authority is bounded twice

    WIF authorizes a workflow to request a token. The mint limits the token, and the repository still decides whether the result can merge.

    OIDC claims

    Verified issuer, audience, repository, and workflow provenance.

    Token mint

    Checks caller, role, level, installation, and requested repositories.

    Capability envelope

    role: coder
    level: read
    repos: org/repository
    perms: contents:read
    expires: short-lived

    Runtime action

    Read, edit, test, comment, or push within the granted capability.

    Repository gate

    Required checks, CODEOWNERS, and branch protection decide whether state advances.

    Role and levelcoder/read is narrower than coder/write
    Repository scopeper-repo callers request their own repository
    Final merge decisiona valid token does not bypass repository policy
    A successful exchange grants a capability. It does not grant a trusted outcome.

    04 · Extension points and architecture

    Custom agents extend behavior below the role boundary

    Agent behavior can grow inside an existing authority envelope. Shared role permissions should grow only under a separate admission bar.

    custom agent path

    Generate, register, test

    The CLI creates a complete, valid starting point instead of leaving plumbing to memory.

    fullsend agent new lint-docs
    --role triage
    agents/ prompt and tools
    harness/ lifecycle and trigger
    schemas/ · policies/ checked output and sandbox
    triage agentown sandbox
    lint-docs agentown sandbox
    shared authority

    Existing served role

    The mint binds the role to a shared permission ceiling and named levels.

    read / write levelsthe level can narrow a role, never widen its App
    closed built-in tablean unknown role fails before useful work begins
    least privilegeeach agent keeps only the scopes its output needs
    A new built-in role is a shared trust boundary, not the default custom-agent extension path.
    controlled delivery

    Output first, control-plane later

    Agent runs produce inspectable artifacts. The caller owns any broader follow-up action.

    Agent sandboxread, edit, test inside the role’s boundary
    fullsend-agent artifactstructured result leaves the run
    workflow_run follow-upuser-owned workflow handles control-plane actions
    A need specific to one agent belongs on a standalone mint. A broadly useful built-in role must pass the shared admission criteria.
    Custom agent behavior grows laterally. Shared authority grows only through an explicit, reviewable role decision.

    05 · Building and contributing safely

    The development loop keeps evidence beside the change

    A green PR should establish the contract for the slice it changes and exercise that contract before merge.

    Slice the change

    Keep the implementation, config, and user-visible behavior together.

    Deploy exact source

    Use `go run` from the checkout and `--vendor` for unreleased workflow testing.

    green PR

    Run matching evidence

    Add behaviour or e2e coverage with the functionality it protects.

    Merge the proven slice

    Keep refs, docs, and tests aligned with the change.

    Practical shortcuts

    Make the path from a local change to a trustworthy run short and repeatable.

    Run `go run ./cmd/fullsend ...` so the CLI matches the checkout.
    Use `--vendor --fullsend-source "$PWD"` to test unreleased workflows in a real repo.
    Keep `uses: @ref` and `fullsend_version` on the same source revision.
    Fix the cause of a timeout or race instead of weakening the suite.
    Green means the declared contract passed its evidence lane. It does not mean every behavior is proven.
